# 每日粗安排与生活场景

Kit 0.11.0 / runtime 2.10.0 / life-camera 0.2.0。继续沿用输入、记忆、情绪、生活、表达、反馈六层。借鉴 dsh-daily-schedule 的粗日程、本地读取和衣着场景连续性，保留本系统既有的事件进程、封存作品、真实阅读与情绪来源。

## 自己的一天

日程的主体固定为 companion。模型在原30m同一次规划中，根据自己的兴趣、精力、待续作品和虚拟生活，选择 busy（忙碌）、overtime（加班赶工）、leisure（休闲）、rest（休息）或 mixed（混合）日型。赶工可以是赶自己的故事、画作或学习项目，生活细节由当前人格发挥。

用户的课表、讲座、工作、日历、睡眠与运动保留用户归属。关心用户、协助提醒与自己的生活安排分别处理。每个意图、活动主题和作品在同一次生成中检查主体，避免把用户刚说的活动自动写成自己的经历，或据此决定自己的忙闲日型。明确约定的共同活动单独记为互动。

主体检查使用当前宿主模型的原规划轮次。结构校验验证subject与日型字段，语义归属由同一次模型判断，后台反馈据真实纠正复核。

## 最短链路

原30分钟生活任务在同一次模型运行中准备全天约8–10个连贯时段，最多12项。剩余半天安排相应减少，兼顾吃饭、收拾、创作、阅读、刷手机与休息的承接，每项用简短一句说明。到点且当前空闲时，明确计划优先接入实际活动，复用原project/stage与手机意图。已有活动正常进行，空档中的自由选择使用life_routine的40/60概率。日程允许临时调整，正在进行的活动仍走life_projects的暂停与未来修订。

原15分钟反馈与30分钟生活任务推进真实已到期阶段，由同一个模型补充当前地点、穿着、手边物品、光线与外观细节。普通聊天直接读取 companion.day_scene 小摘要。生活相机在入队时冻结这个场景，以原三视图为首张实际参考图，后台生成后沿原主聊路径投递。

一张原SQLite保存设置、最多7天的日程和一份当前场景。无新服务、定时任务、模型调用、每天一份文件或前台规划。日程不存情绪，不向原话、经历或回忆表插入未来事件。只有原 life_projects/真实阅读释放的事件进入原情绪评估。

## 正式操作

操作统一为 `op=companion_day, scope=owner-private`，要求 life 模块可用。

| action | 输入 | 返回 |
|---|---|---|
| configure | authorized=true, enabled=true/false | 当前启用状态、日程和场景 |
| pending | 无 | 是否缺今日计划、当前version、可用活动名与字段规范 |
| plan | expected_version, plan | 保存或幂等读回今日计划 |
| repair | authorized=true, expected_version, reason, plan | 纠正已确认的错误意图，可移除错误过去打算，保留修正摘要 |
| scene | expected_version, life_id, fields | 保存或幂等读回真实已释放阶段的场景 |
| status | 无 | 完整今日计划及当前场景，仅后台、明确查询和面板使用 |

新安装及升级默认关闭，宿主经用户选择后显式启用。已有用户批准的部署直接沿用授权。

`plan` 包含 day、subject、day_kind、anchors 四个键。subject必须是companion，day_kind从pending返回的五种日型选择。day为上海时区今天的YYYY-MM-DD，anchors有1–12项。每项只有at、activity、intention，分别为当天严格递增的Unix秒、pending所列活动名、最多140字的打算。新安排的时间必须晚于当前时刻。已有过去打算的时间与内容保留，未来部分可修订。expected_version初次为0，后续为读回版本。日型或内容改变会增加版本；完全相同的计划重试返回replayed。

`status.execution`从已有ct_life和ct_activity_project推导待开始、等待接上、准备中、进行中、完成、错过和撤销。计划时间与实际开始时间分列。稳定ID由日期与计划时间派生，重试沿原项目恢复。当前活动完成后，待执行计划优先接续，跳过原空档等待。未开始且超过90分钟的计划标为错过，由原模型修订未来安排；不会补造过去的完成记录。无需第二份执行状态库。

## 主动分享和后续

明确计划的实际开始在原情绪评估完成后进入分享队列。已分享或交接过开头、进展的活动，结束时将已有结果接入后续。值得说的过程转折由同一次模型自然选择，普通日常可以分享轻微感受。新闻评分与情绪强度分别按自己的规则处理。

原15m分享步骤每轮执行companion_share claim。该入口先将超过15分钟的失联sharing认领标unknown，保留旧lease；再从最近24小时真实已评估的完成事件补齐已开口活动的结果。unknown和旧开头不重发。返回continuity含同一项目、已交接阶段及简短来源，宿主以一两句短话承接后续，使用当前事件原有情绪，不二次评估自己的话。

原lease随后收到真实accepted回执时可从unknown结清。新手机活动的开始与结束共用同一意图身份，自由刷手机也能接上后续。中断在项目登记与开始事件之间时，从原项目时间恢复，保留已经撤销的来源状态。

计划、虚拟活动与真实阅读保持各自来源。只有新开放的发展才会形成新分享。发送使用原主人主聊通路、原贴纸抽签和真实回执；图片仍走原生活相机，选择适合的日常阶段与冻结场景。01–07继续只积累。失联认领的维护也可通过companion_share action=reconcile执行，返回unknown数量，沿既有任务运行。

旧SQLite中没有主体字段的计划仍可通过status读取，pending返回ownership_review_required=true；普通聊天与活动偏好先隔离这份未复核计划。宿主在原后台模型轮次检查归属，沿用户授权调用repair。repair接受完整正确计划，只能保留或移除过去意图，禁止编写另一段过去；原始实际生活与用户日程另行逐项核实。修正只保存原因、时间和撤销的过去时间点，避免错误内容持续进入活动上下文。主体混淆已流入活动/记忆时，按源ID作定向纠正，保留用户真实事项，禁止关键词批量删除。

`scene.fields` 可含 location、clothing、props、light、appearance，每项最多100字。省略表示未知，提交完整当前已知字段，避免意外删掉衣着。life_id 必须对应已有、未撤销、发生时间已到的 ct_life。初次expected_version=0，随后使用当前scene.version。完全相同且base_version相同的重试幂等；过期写入被拒绝，重新读取后决定。禁止把未来计划或封存稿当场景事实。

tick自动跟进已释放活动名称与阶段。新活动保留来源仍有效的已知衣着与外观，清除旧地点、物品和光线，等待同一后台模型确认。缺少记录就保持未知，不按钟点推断已经吃饭或换衣。中断与改计划时仍先调用原companion_activity正式入口。status.scene_version始终返回可写版本，即使旧场景来源已撤销；此时scene为空，旧字段不再继承。

## 宿主接线

1. 保留原15m与30m任务的ID、enabled、目的地、时区、节奏及健康/新闻/阅读分支。普通聊天入口只透传已有 companion.day_scene，不新增读取工具步骤。
2. 30m任务开头调用pending。needed=true时在该轮现有模型运行中生成剩余当天连贯安排并plan；用户要求更密切或需调整时，只改未来部分。接着按原tick、activity pending/plan、情绪评估和阅读流程工作。pending.intention带入当天具体打算，避免活动主题另起炉灶。
3. 15m/30m推进阶段后，如地点、衣着等确有变化，按当前 released life_id 和版本调用scene。每批只提交一次最新场景；没有变化不重复写。只用本轮模型，无独立场景分析模型。
4. 相机plan自动保存scene_snapshot，包括captured_at、场景版本和来源。选取旧阶段时不借用当前场景细节。work必须使用已保存的prompt与实际三视图，禁止生成时重写为后来活动。
5. send_work返回scene_changed及caption_policy。场景已变化时使用“刚才”的说明；已无分享价值可沿原claim settle failed并记录真实撤销原因，省去发送。禁止重生成或重发。原unknown handoff、receipt_work及真实图片回执链完整保留。
6. 原反馈任务每轮完成companion_share claim与真实发送，并在末尾静默覆盖同一个面板。日常详情展示此刻、带实际状态的今日安排、活动过程、分享后续、相机和每批8条历史；小屋、中央原表情和八项概览卡保留。刷新实际native任务定义后，按新架构锁提交私库。

宿主原生final的图片附件若未进入transcript，按相机协议保留unknown，或用主人明确确认该照片的真实消息ID结清。不能把文字轮次当作图片送达证据。

## 继承和性能

day_plan:*、day_scene、day_scene_enabled随原SQLite备份。继承者先验证当前来源和宿主任务，再按用户选择恢复运行。源事件撤销后当前场景不再展示。历史日程只是当时的意图，不能补写成经历。

前台附加值上限以测试约束为900个JSON字符，通常更小，只含当前场景与下一条意图。全日计划、相机历史与回执列表留在后台或面板。实际总回复耗时仍取决于宿主排队、模型和工具，局部读取耗时单独计量。
