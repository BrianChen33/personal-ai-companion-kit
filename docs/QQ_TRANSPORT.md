# 可选 QQ 通道的低占用接线

本通道按用户选择启用。六层伙伴的情绪、生活与表达仍走既有正式入口。

```text
QQ webhook → 短时验签与加密入队 → Redis → 常驻宿主 → 原 inbox / worker
                                                       ↓
                                                 原 SDK / outbox
```

长时间等待消息由常驻宿主承担。Serverless 接收端入队后立即返回，短时 token
代理可以继续使用缓存。通过 HTTP 持续等待数据库也会占用函数的内存时长。

## 部署顺序

1. 核实宿主 Node 版本、真实 SDK、inbox/outbox、去重、空白消息处理与监督进程。
2. 核对实际 Redis host 的 TLS 连通性。需要代理时复用宿主已允许的 CONNECT
   路由，保留证书校验。原生阻塞命令和 REST 兼容列表分别核对。
3. 经用户授权，将原生 Redis 配置用宿主的一次性接收公钥加密交付。解密配置
   放在记忆、工作区和备份范围之外，目录 700、文件 600。日志只报字段与状态。
4. 复用原消费服务，先停旧 HTTP 轮询，再启动唯一 Redis/TLS 消费进程。SDK
   归一化、worker、Markdown、语音、表情概率与回执沿用实际宿主实现。
   核实服务的执行用户与 home。两者和配置所属用户不同时，在服务里明确设置
   `QQ_REDIS_CONFIG_FILE` 的绝对路径。需要宿主批准的出站 CA 时，将既有
   `NODE_EXTRA_CA_CERTS` 传入 Node 启动环境，保持证书校验。这两项同时写入
   既有持久化 service 安装模板，重建 unit 后仍需保留。
5. 确认认证连接、健康时间持续更新与单一进程后，再发布 serverless 的旧
   轮询退役。旧 wait/drain/delete 立即返回 410，token action 保留短时服务。
6. 只读对照真实进程、任务、队列和平台用量。隔离测试使用合成夹具，真实
   消息按正常入口观察。把部署代码 commit 与私库继承说明一起更新。

## 交接可靠性

消息按 FIFO 原子移到 processing 列表，完成本地持久化后确认。中断后先恢复
未确认项。确定性 inbox 文件名与既有去重防止重复工作，seen 记录在落盘后更新。
无法解密的原始密文单独保留，避免阻塞后续消息。保持唯一消费者，关闭客户端
断线后隐式重放命令，设置连接/命令超时和重连退避。

## Blob 退役

按存储桶和近期时间段核对操作量，查实际脚本与任务是否仍调用 list/put。
已停用的旧存储断开项目连接，清除活动部署中多余的 token/store 配置。历史
用量按平台规则退出统计，迁移成功、历史超额与平台恢复日期分别报告。

## Redis 免费额度核对

参考实现空闲时每 25 秒执行一次 `LINDEX` 和一次阻塞 `BLMOVE`，约每天 6,912
条命令，31 天约 214,272 条。真实消息、重连与诊断会另外增加命令。部署时查
实际数据库的月命令、带宽、存储和自动升级设置，结合真实消息与重连次数估算
整月用量。平台统计通常延迟几分钟。

## 可复用实现与继承

参考实现固定在 qq-webhook-bridge 的
`3be8f620db307734970d7fb97859d3269adbc88a`，包含 VM 消费模块、增量宿主补丁、
只读连接检查及部署协议。新宿主先读源码并核接口，已有独立定制逐项保留。
该补丁按审阅过的源码 SHA256 才安装，其他实现需要适配自己的入口。
[实现与协议](https://github.com/BrianChen33/qq-webhook-bridge/tree/3be8f620db307734970d7fb97859d3269adbc88a)

继承可以携带通道代码版本、普通规则与已授权私人数据的索引。账号、密钥、
登录态、收件人身份和通道权限须在新宿主重新授权与绑定。恢复记忆不会自动
启动旧通道或重新发送历史消息。
